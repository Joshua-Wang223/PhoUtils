## 项目简介

**PhoUtils** 是一个面向工程场景的照片处理工具集合，设计原则是：

- **薄封装，重工程**：算法只用 Pillow + numpy，pHash / dHash / aHash 自行实现，不引入 `imagehash` 等额外依赖；脚本负责的是判定策略、资源调度与可观测性。
- **先看清楚，再动手**：默认**只预览不修改**任何文件；真正的写操作要显式 `--apply`。
- **可回退**：默认把冗余文件**移动**到隔离目录 `_duplicates/`，而不是删除；确认无误后一条命令即可还原。
- **智能但不黑盒**：自动探测核数 / 内存、自动决定并发度、自动判"重复"还是"连拍冗余"，但每一步都打印依据，用户可以随时接管。
- **生产可观测**：分阶段打印耗时、并行度、时间保护跳过的候选对数、每组保留/冗余的清晰度数值，并把明细落盘成报告。

## 工具一览

### `photo_dedup.py` — 照片去重

分两个阶段判定，两阶段各自独立：

#### 阶段 1 · 字节级重复

1. 先按**文件大小**分组，只有同大小的文件才计算 SHA-256——绝大多数文件在这一步被排除。
2. 同一哈希的多份文件判为完全重复，**保留文件名最"正"的一份**：带 `(2)` / `（1）` / `copy` / `副本` / `复件` / `拷贝` 后缀的会被判为副本并让位。

字节相同的文件内容一致，清晰度自然也一样，所以这一阶段不需要比清晰度，只看文件名。

#### 阶段 2 · 感知哈希近重复（连拍簇）

1. 为每张图计算三个指纹，并把比特**打包成整数**（后续用 `int.bit_count()` 求汉明距离）：
   - **pHash 256bit**：缩到 32×32 → 二维 DCT → 取左上 16×16 去掉直流分量 → 以中位数为阈值二值化；
   - **dHash 64bit**：缩到 9×8 灰度，比较水平相邻像素；
   - **aHash 64bit**：缩到 8×8 灰度，与均值比较。
2. 每张图额外生成 **90° / 180° / 270°** 三个旋转版本的指纹（应对"同一张图被编辑器转正/转向"的情况）。
3. 两两比较，取 16 种旋转组合中的最小距离。三者**同时**满足阈值才算匹配：
   - `pHash ≤ --phash-dist`（默认 20，共 256 bit）
   - `dHash ≤ --dhash-dist`（默认 10，共 64 bit）
   - `aHash ≤ --dhash-dist`（同上）
4. 匹配对用**并查集**合并成组——这就是"连拍簇"：同一机位、同一姿势的连续多帧，属于内容冗余而非重复文件。
5. 每组保留**拉普拉斯方差最大**的一张（清晰度指标，统一缩放到长边 1024 再比，保证公平），其余标记为冗余。

#### 时间保护

比较之前先看 EXIF 拍摄时间：**双方都有拍摄时间、且相隔超过 `--max-time-gap`（默认 15 秒）时，直接跳过哈希比较**。

- 时间取 `DateTimeOriginal`，叠加 `SubsecTimeOriginal`（子秒）与 `OffsetTimeOriginal`（时区归一，转成 UTC 再比）
- 缺失时退回顶层 `DateTime`
- 两者任一没有拍摄时间 → **不拦**（无法判断就不限制），并在报告中按原因汇总

#### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `folder` | 必填 | 照片目录 |
| `--apply` | off | 真正执行；不加则只预览 |
| `--delete` | off | 直接删除而非移动，必须配合 `--apply` |
| `--dup-dir` | `_duplicates` | 隔离目录名（相对照片目录） |
| `-r`, `--recursive` | off | 递归子目录，自动跳过 `_duplicates` |
| `--no-rotation` | off | 关闭 90/180/270 旋转匹配（更快） |
| `--phash-dist` | 20 | pHash 汉明距离阈值，越小越严 |
| `--dhash-dist` | 10 | dHash / aHash 阈值 |
| `--max-time-gap` | 15 | EXIF 时间保护窗口（秒），`0` 关闭 |
| `--keep` | `sharpest` | 连拍簇保留策略：`sharpest` / `first` |
| `--no-burst` | off | 只做字节级去重，跳过感知哈希 |
| `--sheet` | off | 生成每组对比图到 `_duplicates/` |
| `--exclude` | 空 | 排除文件名含该子串的照片，可重复指定 |
| `--workers` | 0 | 并行进程数，`0`=按核数与内存自动，`1`=串行 |
| `--mem-per-worker` | 0 | 单进程内存预估 GB，`0`=按最大文件推算 |

#### 输出

- 控制台：分阶段结论 + 每组保留/冗余 + 清晰度数值 + 耗时统计
- 文件：照片目录下 `photo_dedup_report.txt`（与屏幕上内容一致，便于归档）

## 快速上手

```bash
# 1) 先预览，什么都不改（永远从这一步开始）
python photo_dedup.py "D:/Photos/2026马拉松"

# 2) 看结果没问题，执行：冗余移到 _duplicates/
python photo_dedup.py "D:/Photos/2026马拉松" --apply

# 3) 顺带生成每组对比图，方便人工复核
python photo_dedup.py "D:/Photos/2026马拉松" --apply --sheet

# 4) 确认 _duplicates/ 里的东西确实不要了，再决定删不删
rm -rf "D:/Photos/2026马拉松/_duplicates"

# 5) 想反悔：把隔离的文件搬回去
mv "D:/Photos/2026马拉松/_duplicates"/*.JPG "D:/Photos/2026马拉松/"
```

## 常见场景配方

### 1. 手机照片 + 网盘重复下载的混装目录

```bash
python photo_dedup.py ./photos --apply
```
字节级阶段会抓出 `IMG_0001(1).JPG` 这类下载副本（保留 `IMG_0001.JPG`），感知哈希阶段抓出连拍冗余。

### 2. 连拍特别多，只想留最锐的

```bash
python photo_dedup.py ./burst --apply --keep sharpest --sheet
```

### 3. 同一场景分多个时段拍摄，担心被误合并

```bash
# 把时间窗收到 5 秒，只合并真正相邻的连拍
python photo_dedup.py ./photos --max-time-gap 5

# 或者明确关掉时间保护（回到纯内容判定）
python photo_dedup.py ./photos --max-time-gap 0
```

### 4. 判定过松 / 过严

```bash
# 过松（合并了不该合并的）：把阈值收紧
python photo_dedup.py ./photos --phash-dist 12 --dhash-dist 6

# 过严（漏掉了明显重复）：放宽
python photo_dedup.py ./photos --phash-dist 28 --dhash-dist 14
```

### 5. 只要最快的精确去重，不要感知哈希

```bash
python photo_dedup.py ./photos --no-burst --apply
```

### 6. 大型图库（数千张），吃满机器

```bash
# 默认就是自动；也可以手动指定并发度与单进程内存预估
python photo_dedup.py ./photos --workers 8 --mem-per-worker 0.4
```

### 7. 整个硬盘的素材目录，递归处理

```bash
python photo_dedup.py "D:/Photos" -r --exclude 截图 --exclude screenshot
```
> 递归模式下各子目录的冗余文件会**统一**移动到根目录的 `_duplicates/` 下；重名自动加 `__1` 后缀，不会覆盖。

### 8. 只要报告，连 `_duplicates/` 都不想产生

```bash
python photo_dedup.py ./photos          # 预览就是纯报告，不产生任何文件
```

## 判定阈值与调参

阈值是**距离上限**，越小越严：

| 阈值 | 默认 | 收紧（更严） | 放宽（更松） | 备注 |
|---|---|---|---|---|
| `--phash-dist` | 20 / 256 bit | 10–14 | 26–30 | 对整体构图最敏感，主要看它 |
| `--dhash-dist` | 10 / 64 bit | 4–6 | 14–18 | 对局部纹理梯度敏感 |
| `--max-time-gap` | 15 s | 2–5 s | 60 s+，或 `0` 关闭 | 只在双方都有拍摄时间时生效 |

调参经验：

- **连拍帧的 pHash 距离通常落在 0–25**（同一机位、姿势微变），所以默认 20 会把"同一姿势的多帧"归为一簇。
- 只要"完全相同的构图"时，把 `--phash-dist` 收到 **10–12**。
- 旋转匹配在阈值边界附近会额外匹配上一些连拍帧——实测 64 张里只有 6 对是"靠旋转才匹配"，且**全部是相隔 0.1–0.2 秒的连拍帧**，没有跨场景误判。如果不需要这个能力，用 `--no-rotation` 关掉更快。

## 并发与资源策略

沿用与 `VidUtils` 一致的思路：**分层探测 → 按"核数 / 内存 / 待处理数"三者取小 → 显式打印依据**。

**核数探测**（依次尝试，取第一个成功的）：

1. cgroup v2 `cpu.max`
2. cgroup v1 `cpu.cfs_quota_us` / `cpu.cfs_period_us`
3. `os.sched_getaffinity(0)`（Linux）
4. `GetProcessAffinityMask`（Windows 亲和掩码）
5. `os.cpu_count()`

**内存探测**：cgroup v2 `memory.max` → `/proc/meminfo` → `GlobalMemoryStatusEx`（Windows）。

**并发度**：

```
内存预算 = min(总内存 × 0.85, 可用内存 − 1.5 GB)
进程数   = min(核数, 内存预算 ÷ 单进程预估, 待处理数)
```

单进程预估未指定时按**最大文件 × 40** 推算 JPEG 解码峰值，夹在 0.25–2.0 GB 之间。

**两阶段各自的并行门槛**（实测定的，不是拍脑袋）：

| 阶段 | 门槛 | 理由 |
|---|---|---|
| 解码 + 哈希 | ≥ 8 张 | 单张约 0.4 s，8 张的收益已经盖过进程池启动开销 |
| 两两比较 | ≥ 3000 张 | 哈希打包成整数后单对只要约 0.7 µs，小库开进程池**反而更慢**（见下表） |

进程池一旦创建失败或抛异常，会**自动退回单进程重跑**，并发相关的失败不会中断任务。

## 安全性设计

照片是不可再生数据，脚本在"动手"这件事上刻意保守：

- **默认干跑**：不加 `--apply` 绝不修改任何文件。
- **危险参数要双确认**：`--delete` 不带 `--apply` 会直接报错退出，不允许"手滑就删"。
- **默认隔离而非删除**：冗余文件移动到 `_duplicates/`，一条 `mv` 即可全部还原。
- **不覆盖任何文件**：隔离目录内重名时自动加 `__1` 后缀。
- **读取失败不致命**：单张图解析失败只记日志并跳过，不会中止整批。
- **留痕**：执行后写 `photo_dedup_report.txt`，记录了保留了谁、淘汰了谁、每张的清晰度。

## 实测数据

本机：8 逻辑核 / 16 GB 内存 / Windows 11（内存受限时并发度自动降到 2–5 进程）。

**解码 + 哈希阶段（并行有效）**

| 规模 | 串行 | 并行 | 说明 |
|---|---|---|---|
| 9 张 | 3.0 s | 1.6–2.0 s | 4 进程 / 2 进程 |
| 43 张 | — | 4.0 s | 8 进程 |
| 64 张 | — | 7.2 s | 5 进程（内存受限） |

**两两比较阶段（打包整数后极快，小库并行反而亏）**

| 规模 | 对数 | 串行 | 并行 4 进程 | 加速比 |
|---|---|---|---|---|
| 200 张 | 1.99 万 | 0.04 s | 1.12 s | 0.03x |
| 1200 张 | 71.9 万 | 0.47 s | 1.18 s | 0.40x |
| 3000 张 | 449.9 万 | 2.19 s | 1.55 s | 1.42x |

并行与串行在 200 / 1200 / 3000 三档、两种时间分布下结果**逐对一致**（已做交叉验证）。

**真实案例**：某次马拉松照片 65 张 → 41 张——1 张字节级重复直接删除，23 张连拍冗余（分属 11 组）移入 `_duplicates/`。
43 张规模的完整判定约 12 秒，其中 903 对候选里有 774 对被时间保护跳过（照片跨 8 个多小时拍摄）。

## 已知限制

- **⚠️ 不要在云挂载盘上执行写操作**。实测环境里 `z:` 盘是 RaiDrive 挂载的云盘，写入是**异步最终一致**的：
  探测文件写入后 5 秒内可见、25 秒后消失，另有一个文件"消失后复活"；并且每次往隔离目录移动文件后，
  云端都会额外生成一份 `xxx(1).JPG` 冲突副本（两批共 22 个）。**建议**：
  - 在本地磁盘上处理，处理完再同步回云端；
  - 或先暂停 / 卸载同步客户端（RaiDrive、OneDrive 等）再执行 `--apply`；
  - 只做预览（不加 `--apply`）是安全的，纯读。
- **感知哈希无法区分"重复"和"同场景连拍"**。工具把后者也归为冗余，这是**刻意的**（连拍多帧通常只需要一张），
  但如果你就是要保留同一姿势的多帧，请用 `--max-time-gap 0 --phash-dist 10` 把判定收紧到"几乎相同"。
- **HEIC / RAW 支持取决于 Pillow 的解码能力**。扩展名清单里留了 `.heic` / `.cr2` / `.nef` / `.arw` 等，
  但普通 Pillow 装包未必带解码器；解不开的文件会被跳过并打印原因，不影响其他文件。
- **清晰度是启发式指标**。拉普拉斯方差对运动模糊、逆光、主体大小都敏感，只能当作"同机位同姿势多帧之间谁更清晰"的相对参考。
  实测中确实出现过清晰度差在 1–2 之间的"平手"（如 431 vs 430），这类选择建议人工看一眼 `--sheet` 出的对比图。
- **旋转匹配会增加边界匹配**。见[判定阈值与调参](#判定阈值与调参)，介意就 `--no-rotation`。
- **时间保护依赖相机时钟准确**。多机位拍摄时各机身时钟若有偏差，跨机身的真重复可能被误拦；此时用 `--max-time-gap 0` 关掉。

## 路线图（Roadmap）

PhoUtils 规划作为一个**命令行优先 / Python 原生**的照片工程工具集：

| 模块 | 状态 | 说明 |
|---|---|---|
| `photo_dedup.py` | ✅ 已发布 | 照片去重：字节级 + 感知哈希 + EXIF 时间保护 + 多进程 |
| `photo_rename.py` | 🚧 规划中 | 按 EXIF 拍摄时间批量重命名（含时区/序号模板），自动处理重名 |
| `photo_organize.py` | 🚧 规划中 | 按日期/相机/事件归档到 `YYYY/MM/DD` 目录树 |
| `photo_exif.py` | 🚧 规划中 | EXIF 批量查询 / 清洗 / 迁移（含隐私字段脱敏） |
| `photo_convert.py` | 🚧 规划中 | HEIC → JPEG、批量缩放、水印、格式统一 |
| `photils` | 💭 设想中 | `ls` 替代品，列目录时顺带显示分辨率 / 拍摄时间 / 相机 / 镜头 / ISO / 快门 |
| `phoutils-cli` | 💭 设想中 | 统一 CLI 入口，子命令分发 `phoutils dedup / rename / organize …` |

**统一设计约束（所有后续模块都会遵守）：**

- 参数命名风格一致（`--apply` / `--dry-run` / `--dup-dir` / `--workers` / `--exclude`）
- 默认**只读预览**，写操作一律要 `--apply`
- 批量语义一致（目录 / 递归 / 排除规则）
- 失败诊断一致（跳过并打印原因，不中断整批）
- 资源策略一致（cgroup 感知的自动探测 + `--workers` / `--mem-per-worker` 覆盖）
- 可回退一致（默认隔离到 `_duplicates/`，而非直接删除）

## 工程记忆（memory/）

`memory/` 放的是**工具背后的事实与踩坑**，不是 API 文档——用法看本文件，为什么这么做、踩过什么坑看那里。
索引在 [`memory/MEMORY.md`](memory/MEMORY.md)，写法沿用本机 codebuddy 自动记忆的约定
（frontmatter 带 `name` / `description` / `type`，正文用「事实 → **Why:** → **How to apply:**」）。当前条目：

- [云挂载盘的写入不可信（RaiDrive 挂 z: → Quark）](memory/project_cloud_mount_write_hazard.md)
  —— 写入异步最终一致：探测文件 t+5s 还在、t+25s **自己消失**，一个被删的文件**复活**；
  每次往 `_duplicates/` 移动文件，云端就补一份 `xxx(1).JPG`（两批 21→20、2→2，均字节相同），
  且副本时间戳**早于**正本。结论：在这类路径上批量改文件前必须先提醒用户，纯预览是安全的
- [感知哈希的并行收益与直觉相反](memory/project_phash_parallel_payoff.md)
  —— 哈希打包成整数用 `int.bit_count()` 比对，单对仅约 0.7 µs，比较阶段的瓶颈是**进程池启动**：
  1200 张时并行 **0.40x**、3000 张才 **1.42x**，故门槛定在 3000 张；附带记下测这类代码的四个坑
- [Windows 亲和掩码探测的伪句柄坑](memory/project_windows_affinity_probe.md)
  —— `GetCurrentProcess()` 返回 `-1`，ctypes 默认按 `c_int` 截断成 `0xFFFFFFFF` 成为无效句柄，
  `GetProcessAffinityMask` 静默返回 0 并悄悄降级到 `os.cpu_count()`；必须 `c_void_p(-1)`。
  教训：探测结果要**带上来源字符串并打印**，否则这类静默降级发现不了

## 常见问题（FAQ）

**Q1：会不会误删照片？**

不会直接删。默认只做预览；`--apply` 也只把冗余文件**移动**到 `_duplicates/`。要真删得同时给 `--apply --delete`。

**Q2：为什么"连拍的不同帧"也被算成重复？**

因为对绝大多数使用场景来说，同一姿势的连续 N 帧只需要一张，属于**内容冗余**。工具把它们并成"连拍簇"后只留最锐的一张。
如果你要全部保留，用 `--phash-dist 10 --max-time-gap 0` 收紧到"几乎相同才算重复"。

**Q3：`--max-time-gap` 会不会把真正的重复挡掉？**

同一次导入的重复副本（如 `IMG_0001(1).JPG`）会被**阶段 1 的字节级判定**抓住，不受时间保护影响。
时间保护只作用于阶段 2 的内容近似判定。另外只要任一方没有 EXIF 拍摄时间，就不拦。

**Q4：为什么两组照片隔着 8 小时也没被合并？**

时间保护生效。该目录里 903 对候选中有 774 对被跳过——这正是它存在的意义：避免把"同一构图不同时刻"的照片并簇。

**Q5：为什么输出里说"并行 2 进程"，我明明有 8 核？**

内存是瓶颈。可用内存不足时，`内存预算 ÷ 单进程预估` 会小于核数，此时取小值。可以把其他占内存的程序关掉，
或者用 `--mem-per-worker` 说明你的实际单进程占用（默认按最大文件 × 40 估算，偏保守）。

**Q6：比较阶段为什么默认不并行？**

因为不划算——见[实测数据](#实测数据)：1200 张时并行只有串行的 0.40x，3000 张才转为 1.42x。
门槛设 3000 张，常见规模走串行更快。

**Q7：`--sheet` 生成的对比图放哪了？**

`_duplicates/dup_groupNN.jpg`，每组一张，从左到右是组内所有帧，文件名标在每张图上方。

**Q8：报告文件会被自己重复处理吗？**

不会。报告是 `.txt`，不在图片扩展名清单里。

**Q9：递归模式下 `_duplicates/` 会被扫描吗？**

不会，`-r` 会跳过名为 `_duplicates` 的目录（可用 `--dup-dir` 改名，改名后按新名字跳过）。

**Q10：支持视频或动图吗？**

不支持。只处理静态图片；视频请用同级项目的 `VidUtils`。

## 贡献指南

欢迎以 Issue / PR 的形式参与：

1. **提 Bug**：请附上 `python -V`、`pip show pillow numpy` 的版本、完整命令行，以及预览模式（不加 `--apply`）的输出。
2. **提新功能**：优先对齐[路线图](#路线图roadmap)中已规划的模块；新模块请先发 Issue 讨论接口设计，以保持参数风格统一。
3. **代码风格**：遵循 PEP 8，函数级中文 docstring，关键分支要有 inline 注释说明"为什么这样写"而不仅是"在做什么"。
4. **测试**：新增参数分支至少覆盖 happy path + 一个边界 / 失败 case；判定逻辑（阈值、时间保护）建议用"同一张图改 EXIF 时间"的合成样本做端到端回归。
5. **阈值默认值**：改动 `--phash-dist` / `--dhash-dist` / `--max-time-gap` 默认值前，请在 README 的[实测数据](#实测数据)里补上对照实测。
