## 事实（2026-09-17 实测，两轮独立观察 + 一次受控探测）

`z:/quark1/` 是 **RaiDrive 挂载的 Quark 云盘**。同机还跑着 `aDrive`、`OneDrive`、`dingpan_sync`
（钉盘）等同步进程，但产生下面现象的是 RaiDrive 这条链路。

**受控探测**（在 `_duplicates/` 里写入文件后观察）：

| 时间点 | `probe_test.JPG` | 备注 |
|---|---|---|
| t+0 | 存在 | `cp` 返回 0 |
| t+5s | 存在 | |
| t+25s | **不存在** | 无人删除，自己消失 |

同一轮里，一个**此前已被删除**的探测文件 `__probe_copy.JPG` 在后续 `ls` 中**重新出现**。
另有一次 `ls | grep` 完全看不到刚 `cp` 进去的文件。

**冲突副本**：每次用 `shutil.move` 把文件移进 `_duplicates/`，云端都会额外生成一份 `xxx(1).JPG`：

| 批次 | 移动数量 | 生成的 `(1)` 副本 |
|---|---|---|
| 第一批（15:36–15:37） | 21 | 20 |
| 第二批（16:21） | 2 | 2 |

时间戳显示副本与正本几乎同时出现（例：`3N8A0301(1).JPG` ctime 16:21:12，`3N8A0301.JPG` ctime 16:21:15；
`IMGI6905(1).JPG` 16:21:15，`IMGI6905.JPG` 16:21:18），**副本在前、正本在后**，
说明这是云端/客户端对同一次操作的重放或去重竞争，不是本地脚本的 bug。

两批共 22 个 `(1)` 副本均逐一比过 SHA-256，与同名文件**字节完全相同**。
`photo_dedup.py` 的移动逻辑只会产生 `__1` 后缀（重名避让），**从不产生 `(1)` 后缀** ——
`(1)` 一定是外部产生的。

## Why

照片是**不可再生数据**。在异步最终一致的文件系统上做批量改文件，本地看到的目录状态与云端不一致：
文件"消失/复活"意味着**本地判定的结果不能代表云端最终状态**，最坏情况是删了不该删的、
或者以为保留了的其实没上去。而且这类问题**静默发生**——脚本退出码是 0，不报任何错。

## How to apply

- **写操作前必须提醒用户**：在 `z:/quark1/` 或任何云挂载路径上执行 `--apply`（或任何批量改文件的动作）之前，
  先说明这个风险，并建议：
  1. 拷到本地磁盘处理，处理完再同步回去（推荐）；
  2. 或先暂停 / 卸载 RaiDrive（及其他同步客户端）再执行；
  3. 或改用不写文件的模式。
- **纯读是安全的**：`photo_dedup.py` 不加 `--apply` 的预览不产生任何写入，可以放心跑。
- **看到 `xxx(1).JPG` / `xxx(2).JPG` 时的处置**：先取同名文件比 SHA-256，**确认字节相同再删**。
  不要因为"名字像副本"就直接删——本项目的 `canon_rank()` 也是按这个原则（副本让位）实现的。
- **写完后要复查**：执行完 `--apply` 后重新列一遍目录，确认正本都在、没有凭空多出的 `(1)`；
  必要时重跑一次预览，与上一次的报告比对。
- 判断某个盘是不是这类挂载：`Get-Process` 里查 RaiDrive / OneDrive / aDrive 等客户端，
  或看盘符（`z:` 由 RaiDrive 创建）。Linux 侧对应的是 FUSE 挂载。
